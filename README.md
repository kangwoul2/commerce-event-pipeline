# Commerce Event Pipeline

기존 전자상거래 분석 프로젝트를 확장해, 실시간으로 들어오는 구매 이벤트를 **Spring Boot → Kafka → 멱등 소비자 → PostgreSQL 집계** 구조로 처리한 이벤트 기반 백엔드 프로젝트입니다.

초기 프로젝트에서는 SQL과 Excel을 이용해 지역, 상품, 기온 데이터를 결합하고 판매 패턴을 분석했습니다. 이후 실제 서비스에서는 분석용 데이터가 어떻게 생성되고, 중복 전달이나 동시 처리 상황에서도 집계 결과를 어떻게 안전하게 유지할 수 있는지로 문제를 확장했습니다.

이 저장소의 핵심 질문은 다음과 같습니다.

> **동일한 구매 이벤트가 네트워크 재시도나 Kafka 재전달로 여러 번 도착해도 매출 집계에는 한 번만 반영하려면 어떻게 설계해야 하는가?**

---

## 1. 핵심 구조

```text
클라이언트
  │
  │ POST /api/v1/purchases
  │ Idempotency-Key: UUID
  ▼
Spring Boot API
  │
  │ 이벤트 발행
  ▼
Kafka 주제: purchase-events
  │
  ▼
PurchaseEventConsumer
  │
  ▼
집계 처리 서비스
  │
  ├─ processed_events
  │    └─ 중복 이벤트 확인
  │
  └─ regional_sales
       └─ 지역별 매출 원자적 갱신
```

구매 API는 최종 매출 집계까지 기다리지 않고 `202 Accepted`를 반환합니다. 이후 Kafka 소비자가 이벤트를 받아 PostgreSQL의 지역별 매출 집계를 갱신합니다.

이 프로젝트의 핵심 개념은 다음 네 가지입니다.

- Kafka를 이용한 비동기 이벤트 처리
- 최소 한 번 전달 환경에서의 멱등성 보장
- 데이터베이스 유일성 제약조건을 이용한 중복 방지
- 원자적 갱신과 트랜잭션을 이용한 집계 정합성 유지

---

## 2. 왜 Kafka를 사용했는가

Kafka를 단순히 "대용량 처리를 위해서" 사용한 것은 아닙니다.

구매 API에서 지역별 매출 집계까지 모두 동기적으로 처리하면 사용자 요청과 분석 작업이 강하게 결합됩니다. 분석 외에도 추천, 알림, 감사 로그처럼 동일한 구매 이벤트를 사용하는 기능이 늘어나면 API의 책임도 계속 커집니다.

Kafka를 사용하면 구매 이벤트를 기록해 두고 여러 소비자 그룹이 독립적으로 처리할 수 있습니다.

### API에서 바로 DB 집계를 갱신하는 경우

장점:
- 구조가 단순함
- 즉시 결과가 반영됨

단점:
- 구매 요청 지연시간이 집계 작업에 영향을 받음
- 후속 기능이 늘수록 API 책임이 커짐
- 후속 처리 장애가 사용자 요청까지 전파될 수 있음

### 일반 DB 대기열을 사용하는 경우

장점:
- 작은 규모에서는 구현이 단순함

단점:
- 여러 소비자 그룹과 재처리 요구가 늘어날수록 관리가 복잡해짐

### Kafka를 사용하는 경우

선택 이유:
- 이벤트를 지속적으로 보관할 수 있음
- 소비자 그룹별로 독립적인 처리가 가능함
- 파티션 내부 순서를 보장함
- 필요하면 과거 이벤트를 다시 처리할 수 있음

따라서 이 프로젝트에서는 구매 요청 처리와 지역별 매출 집계를 분리하기 위해 Kafka를 사용했습니다.

## 3. API 처리 흐름

### 구매 이벤트 등록

```http
POST /api/v1/purchases
Idempotency-Key: 3c0c6c8e-...
Content-Type: application/json
```

```json
{
  "customerId": 1001,
  "category": "Outerwear",
  "region": "New York",
  "amount": 129.90
}
```

응답:

```http
202 Accepted
```

```json
{
  "eventId": "3c0c6c8e-...",
  "status": "ACCEPTED"
}
```

`202 Accepted`를 사용하는 이유는 HTTP 응답 시점에 최종 매출 집계까지 완료되었다고 보장하지 않기 때문입니다.

### 지역별 매출 조회

```http
GET /api/v1/analytics/regions
```

이 API는 Kafka 소비자가 만들어 둔 PostgreSQL 지역별 매출 집계 결과를 조회합니다.

---

## 4. 이벤트 구조

`PurchaseEvent`는 후속 처리에 필요한 최소 정보를 담습니다.

```text
eventId
customerId
category
region
amount
occurredAt
```

가장 중요한 값은 `eventId`입니다.

Kafka는 일반적으로 최소 한 번 전달 방식으로 사용할 수 있기 때문에, 소비자가 데이터베이스 반영까지 끝낸 뒤 오프셋 커밋 전에 종료되면 같은 이벤트가 다시 전달될 수 있습니다.

따라서 이 프로젝트에서는 "이벤트가 한 번만 전달된다"고 가정하지 않고, **같은 이벤트가 다시 들어와도 결과가 한 번만 반영되도록 멱등성을 보장**합니다.

---

## 5. 멱등 소비자

동일한 이벤트가 여러 번 들어오는 경우 다음과 같이 처리합니다.

```text
이벤트 A 도착
   ↓
processed_events에 event_id 저장 시도
   ↓
┌────────────────┬────────────────┐
│ 새 이벤트      │ 이미 처리된 이벤트 │
└───────┬────────┴───────┬────────┘
        │                │
        ▼                ▼
지역별 매출 증가       종료
```

`PurchaseProjectionService`는 하나의 트랜잭션 안에서 다음 작업을 수행합니다.

1. `processed_events.tryInsert(eventId)`로 이벤트 ID 저장 시도
2. 이미 존재하는 ID라면 중복 이벤트로 판단하고 종료
3. 새 이벤트라면 `regional_sales` 증가

핵심은 Kafka 소비자가 한 번만 호출되는 것을 기대하는 것이 아니라 **최종 데이터베이스 반영 결과가 한 번만 발생하도록 만드는 것**입니다.

---

## 6. 왜 Redis 분산 락 대신 DB 유일성 제약조건을 사용했는가

중복 이벤트를 애플리케이션 메모리의 `Set<UUID>`로 기록할 수도 있습니다. 하지만 서버가 여러 대라면 메모리를 공유하지 못하고, 서버가 재시작되면 기록도 사라집니다.

그래서 PostgreSQL의 `processed_events.event_id`를 기본 키로 사용합니다.

```text
processed_events
└─ event_id PRIMARY KEY
```

같은 이벤트 ID가 동시에 저장되려고 해도 데이터베이스의 유일성 제약조건이 최종적으로 하나만 허용합니다.

Redis 분산 락도 동시 실행을 제어하는 방법이지만, 이 프로젝트의 문제는 "한 작업에 한 명만 들어가게 할 것인가"보다 **"같은 이벤트의 결과가 두 번 반영되지 않게 할 것인가"**에 가깝습니다.

따라서 유일성 제약조건과 트랜잭션이 더 직접적인 해결책이라고 판단했습니다.

---

## 7. 갱신 손실 방지

지역별 매출은 여러 이벤트가 동시에 같은 지역을 갱신할 수 있습니다.

다음 방식은 위험합니다.

```text
SELECT total
애플리케이션에서 total += amount
UPDATE total
```

두 요청이 동시에 같은 기존 값을 읽으면 나중에 저장한 값이 앞선 증가분을 덮어쓰는 **갱신 손실**이 발생할 수 있습니다.

그래서 PostgreSQL에서 한 문장으로 값을 증가시키는 원자적 갱신 방식을 사용합니다.

핵심 원칙은 다음과 같습니다.

> 공유 값을 증가시킬 때 가능하면 값을 읽어서 애플리케이션에서 계산한 뒤 다시 저장하지 않고, 데이터베이스가 한 번에 갱신하도록 한다.

---

## 8. 파티션 키를 지역으로 정한 이유

Kafka는 주제 전체가 아니라 **같은 파티션 안에서만 순서**를 보장합니다.

이 프로젝트에서는 지역별 매출을 집계하기 때문에 `region`을 메시지 키로 사용합니다.

```text
New York 이벤트   → 같은 파티션
Texas 이벤트      → 같은 파티션
California 이벤트 → 같은 파티션
```

장점:
- 같은 지역의 이벤트가 같은 파티션으로 들어감
- 지역별 처리 순서를 유지하기 쉬움

단점:
- 특정 지역에 이벤트가 몰리면 한 파티션에 부하가 집중될 수 있음

실제 트래픽이 특정 지역에 심하게 편중된다면 `region + bucket` 같은 방식으로 키를 더 세분화할 수 있습니다. 다만 이 경우 지역 전체에 대한 엄격한 순서 보장은 약해질 수 있습니다.

---

## 9. 트랜잭션 범위

다음 두 작업은 하나의 데이터베이스 트랜잭션으로 묶습니다.

```text
BEGIN
  INSERT processed_event
  UPDATE regional_sales
COMMIT
```

만약 `processed_events` 기록만 성공하고 지역별 매출 갱신이 실패한 상태로 저장된다면, 다음 재시도에서는 이미 처리된 이벤트로 판단되어 실제 매출 반영이 영원히 누락될 수 있습니다.

따라서 **중복 처리 기록과 실제 집계 갱신은 함께 성공하거나 함께 취소되어야 합니다.**

## 10. 주요 장애 상황

### 10-1. 이벤트 발행 실패

구매 API가 이벤트를 Kafka에 발행하는 과정에서 실패하면 정상적으로 `202 Accepted`를 반환해서는 안 됩니다.

향후 실제 주문 데이터베이스 변경과 Kafka 이벤트 발행을 함께 보장해야 한다면 트랜잭셔널 아웃박스 패턴을 사용할 수 있습니다.

```text
하나의 DB 트랜잭션
  ├─ 주문 상태 저장
  └─ 발행할 이벤트 저장
        ↓
별도 발행 작업
        ↓
Kafka
```

현재 프로젝트는 완전한 주문 시스템이 아니기 때문에 아웃박스를 구현 완료 기능처럼 설명하지 않습니다.

### 10-2. DB 반영 후 오프셋 커밋 전에 소비자가 종료

```text
이벤트 처리 완료
↓
DB 반영 완료
↓
오프셋 커밋 전 종료
↓
Kafka가 같은 이벤트 재전달
```

이 경우 `processed_events`의 이벤트 ID가 이미 존재하므로 두 번째 매출 증가는 발생하지 않습니다.

### 10-3. 반복해서 실패하는 메시지

형식 오류나 업무 규칙 위반처럼 재시도로 해결되지 않는 메시지는 계속 반복 처리하면 안 됩니다.

현재는 완전한 DLQ 운영 구성을 구현하지 않았으며, 실제 운영 환경에서는 재시도 횟수를 제한하고 실패 메시지를 DLQ로 격리하는 방식이 적합합니다.

### 10-4. Kafka 장애

현재 구조는 Kafka 사용 가능 여부에 직접 의존합니다. 주문 저장과 이벤트 발행을 분리해야 하는 실제 서비스라면 아웃박스 같은 영속 저장 방식을 추가로 검토해야 합니다.

## 11. 중복 이벤트 재전송 실험

`experiments/replay_duplicate.py`는 동일한 이벤트 ID를 반복해서 전송해 멱등성이 실제로 지켜지는지 확인하기 위한 실험 코드입니다.

검증 질문:

```text
같은 UUID의 이벤트를 N번 전송하면
regional_sales는 몇 번 증가하는가?
```

기대 결과:

```text
요청 횟수: N
실제 집계 반영 횟수: 1
```

검증 시 확인할 값:
- 중복 요청 횟수
- `processed_events` 행 수
- `regional_sales` 증가량
- 소비자 오류 수

측정하지 않은 처리량 수치는 문서에 사용하지 않습니다.

## 14. 정확히 한 번 처리라고 표현하지 않는 이유

이 프로젝트에서는 "Kafka를 사용해서 정확히 한 번 처리했다"고 표현하지 않습니다.

Kafka와 외부 PostgreSQL을 함께 사용하는 상황에서는 생산자 설정 하나만으로 전체 시스템의 정확히 한 번 처리가 자동으로 보장되지 않습니다.

현재 구현이 보장하는 범위는 다음과 같습니다.

> **같은 이벤트 ID가 다시 전달되더라도 PostgreSQL의 지역별 매출 집계에는 중복 반영되지 않도록 멱등성을 구현했다.**

## 15. 프로젝트 발전 과정

```text
1단계
전자상거래 원본 데이터
→ SQL / Excel 분석
→ 지역별 판매 특성 확인

2단계
"실서비스에서는 이 데이터가 어떻게 생성되는가?"
→ 구매 API 구현

3단계
구매 요청과 집계 작업이 결합되는 문제 발견
→ Kafka를 이용해 비동기 처리

4단계
최소 한 번 전달에서 중복 이벤트 발생 가능
→ eventId + processed_events로 멱등성 보장

5단계
동시 집계에서 갱신 손실 가능
→ 데이터베이스 원자적 갱신

6단계
중간 장애 상황 검토
→ 트랜잭션, 아웃박스, DLQ 적용 범위 정리
```

## 16. 면접에서 설명할 핵심

이 프로젝트에서 Kafka 자체보다 중요한 것은 **장애와 중복 전달을 예외 상황이 아니라 정상적으로 발생할 수 있는 상황으로 보고 설계한 것**입니다.

정리하면 다음 흐름으로 설명합니다.

```text
문제
→ 같은 이벤트가 여러 번 전달될 수 있음

선택
→ eventId를 DB 기본 키로 기록

보장
→ 이미 처리한 이벤트는 다시 집계하지 않음

추가 문제
→ 중복 기록과 집계 갱신 사이에서 장애가 날 수 있음

해결
→ 두 작업을 하나의 트랜잭션으로 묶음

추가 문제
→ 여러 이벤트가 같은 지역 매출을 동시에 갱신할 수 있음

해결
→ DB 원자적 갱신으로 갱신 손실 방지
```

## 17. 현재 한계

현재 프로젝트는 실제 결제 시스템 전체를 구현한 것은 아닙니다.

- 결제 승인 기능 없음
- 재고 정합성 처리 없음
- 아웃박스 미구현
- DLQ 운영 정책 미완성
- 다중 브로커 운영 환경 미구축
- 실제 대규모 처리량 실측 미완료

대신 이벤트 기반 백엔드에서 핵심적으로 발생하는 **중복 전달, 동시 갱신, 중간 장애 상황에서 데이터 정합성을 지키는 방법**을 코드로 검증하는 데 초점을 맞췄습니다.
